# Amended S0 history check (v2): frozen pre-run protocol (2026-11)

**Status:** written 2026-11-27, before any v2 run exists. Frozen at the commit that adds this file together with `docs/cluster/aider-pilot/05_s0_history_check_v2.py`, `05_s0_history_check_v2.sbatch` and `tests/test_s0_history_check_v2.py`; the submitted job records the runner SHA-256, the v1 runner SHA-256 and the source commit in its artifact. Nothing here may be loosened after the artifact is read. Later changes must be dated, state what changed, and be written without reference to which outcome they would favour. This is a protocol amendment in the sense of Sec. 5 of `s0-history-check-decision-plan-2026-11.md`. The originals (`04_harbor_s0_history_check.py/.sbatch`, the v1 report and the decision plan) are not modified.

**Scope.** Engineering evidence about an interface and a harness. No performance claim of any kind is made or permitted: not Aider Polyglot, not Terminal-Bench, not "S0 works", not "history length is harmless". No model has been run for v2 at the time of writing.

## 1. Motivation: what the first run did and did not show

The first run (job 4944139, six synthetic conversations, 8,192-token server window) left three problems, all stated in `s0-harbor-history-check-2026-11.md`:

1. **7 of 20 requests (35%) returned no tool call** (one or two per conversation, each producing an `invalid` step). The cause is unknown. Under decision-plan row R3 (> 20%) this blocks any pilot until it is understood.
2. **The "long" condition was void.** S0 truncates every observation to `max_observation_chars = 4000`, so the 260-repeat README was cut to the same size as the 80-repeat one and both prompts measured 1,386 tokens. The v1 contrast of short versus long history contains no information.
3. **Per-request order, `finish_reason` and reasoning-token counts were not recorded**, so "no tool call" cannot be separated into (a) output cap exhausted by reasoning, (b) a prose answer without a tool call, (c) a template/parser failure, or (d) something else; and a no-tool reply followed by a valid one (recovery) cannot be told apart from a conversation that stays stuck.

A fourth, structural weakness was named in the decision plan (Sec. 6): the short/long contrast was confounded with trajectory divergence, because the two arms already differ at the first request, and three pairs cannot balance order.

### 2.1 Why 32,768 and not more or less

- **Why not 8,192.** v1 already showed the window is arithmetically tight: with a 1,024 cap and a 1,024 margin only about six thousand tokens of history remain, so a long-history arm would measure the guard, not the model (decision plan R6/R7, Sec. 6).
- **Memory is not the constraint.** The serving sweep (`serving-sweep-2026-11.md`) loaded the same model family at 65,536 tokens per slot on the L40S: job 4504968 (1 slot, q8_0) peaked at 22,107 MiB with 23,961 MiB free; job 4505001 (4 slots, f16) peaked at 26,661 MiB with 19,407 MiB free; the document states all twelve screened settings fit with at least 16.8 GiB of headroom. One slot at 32,768 needs less KV cache than any of those. The v1 run at 8,192 kept at least 34,295 MiB free. The sweep's build and flags are not verified to be identical to the pinned `b11515` image used here, so the 1 GiB VRAM guard stays the arbiter, not this argument.
- **Why not 65,536.** It is not needed in the expected case and would weaken the guard's role as a tripwire. Expected arithmetic (an estimate, not a measurement): base prompt about 800 to 900 tokens; a four-terminal conversation adds four long-arm observations of <= 3,600 characters (the counter plus 16-hex records tokenise at roughly 2.5 characters per token, so about 1.3k to 1.5k tokens each) plus four completions (usually 100 to 300 tokens, <= 1,024), for an expected peak near 8k tokens at the fifth request, far below the 30,720-token guard threshold. The window only matters if the model loops: eleven further long-arm turns could reach roughly 20k to 25k. **If the guard fires in the long arm this is deterministic arithmetic, recorded as `context_guard`, and not model behaviour.**

## 3. Design

Eight conversations, pair p = 1..4, conditions {short, long}, execution order short-first in pairs 1 and 3, long-first in pairs 2 and 4. The real `HarborStrategyAgent` and the real model client run against `MockEnvironmentV2`: the first `exec` returns a fixed workdir string (S0 probe 1), the second returns the shared README (S0 probe 2), later calls return `synthetic_terminal_output(condition, n)`. The command string is never stored, inspected or executed. The agent's step writer is replaced by an aggregate-label writer, so no `aas_steps.jsonl` is created. The runner measures preflight prompt tokens through the server's token-count route (falling back to apply-template plus tokenize), as in v1.

## 4. Hypotheses and predeclared readings

All are descriptive; n = 4 pairs, 8 conversations, at most 96 requests, one model, one seed root, one GPU.

- **H1 (paired first replies).** Pair members have identical first prompts (checked by token count) and identical seeds. Reported: for each of the 4 pairs, agreement or disagreement of the first-reply category, and the first-reply no-tool count among the 8 first requests, set beside (but not compared with) v1's rate. Causes of any disagreement (sampling-seed handling, KV/prompt-cache state, batching) are not separable in this design, and agreement does not show determinism.
- **H2 (mechanism of no-tool replies).** For each no-tool request, the joint record of `finish_reason`, `output_cap_reached`, reasoning tokens (or chars), and `content_chars`. Readings declared in advance, each only "consistent with": (i) `finish_reason = length` with cap reached and reasoning dominating: output cap/reasoning budget; (ii) `finish_reason = stop` with `content_chars > 0` and no call: the model answered in prose; (iii) `stop`, empty content, non-empty reasoning: template/parser or channel handling; (iv) none of these. A pattern outside these four is reported as such.
- **H3 (recovery).** Of all no-tool replies, the number `recovered`, `not_recovered`, `no_next_request`. Triage reading: any conversation that ends at the ceiling with a no-tool reply never followed by a valid call is a loop-level concern even if its rate is low.
- **H4 (growth validity; a gate, not a finding).** Long history must be materially larger than short (Sec. 6, G4). H4 is a property of the harness, not of the model.
- **H5 (exploratory).** Descriptive comparison of no-tool rate per request and of submit and guard counts between conditions, conditional on gate pass. No test, interval or effect size is computed; the plan's R8/R9 wording applies (a difference is a hypothesis, no difference is non-discrimination).

Decision-plan rows R1 to R3 and R5 to R7 keep their wording and thresholds as **engineering triage triggers**, with R6/R7 evaluated against the 32,768 window, and with H2/H3 read before R3 is applied. R10 is not available from a non-VALID verdict. Any pattern not covered defaults to "do not proceed; write a dated note".

## 5. Recorded metrics (aggregate only)

Per conversation: condition, pair, effective seed, strategy hash, S0 budgets and `max_observation_chars`; `stop_reason`; request count; ordered lists `category_order`, `tool_order`, `finish_reason_order`, `completion_tokens_order`, `reasoning_tokens_order`, `prompt_tokens_order`; per request the fields in A (a) plus timings; `recovery` summary; `terminal_turn_growth_deltas`; mock exec counts (workdir, README, terminal), `terminal_output_chars` and 12-hex-character hashes of each fixed output; `step_categories`; `tripwire_flags` (counts); `context_guard` object; `submitted`, `submit_step`; safety fields. Run level: hashes (model, server image, runner, v1 runner, instruction, strategy), source commit, GPU peak/minimum-free, `unexpected_process_spawns`, `aggregate_only_violations`, `validity` object. As in the decision-plan addendum, the `model_error` step count includes guard and ceiling stops; provider failures are counted only from `stop_reason` starting with `error:`.

Never recorded or written: prompts, completions, commands, tool arguments, answers, reasoning text, observation text, message content, tool-call ids.

## 6. Validity gate and stop rules

The gate is computed inside the artifact (`validity.verdict`). **INVALID overrides every interpretation; INVALID results are discarded for inference and only the failure is reported.**

- **G1 (no real executor, no raw content).** INVALID if any of: a subprocess other than `nvidia-smi` was launched during the run (counted by a `subprocess.Popen` wrapper); any `harbor.*` module whose name matches trial/verifier/orchestrat/docker/environments was newly imported during the run; `agent_step_log_created`, or any NEW step-log-like entry (`*.jsonl`/`*.ndjson`, names containing "step", or starting `aas_`) in a conversation's log directory (entries that existed after agent construction, e.g. created by Harbor's base class, are ignored); `mock_exec_calls` differing from workdir + README + terminal mock counts; S0 probes not intercepted before the first request; any recorded observation longer than S0's 4,000 characters; any string leaf longer than 64 characters or any key named `content`, `prompt`, `completion`, `command`, `reasoning`, `arguments`, `messages`, `observation`, `answer` or `text` anywhere in the per-conversation records.
- **G2 (pairing).** INVALID if a pair's effective seeds differ, if the first-request prompt **token counts** of a pair differ (token counts are compared, not content hashes, so equal counts do not prove identical text; identity is by construction), or if the executed order is not short-first in exactly 2 of the 4 pairs.
- **G3 (completeness).** `INCOMPLETE` (not INVALID) if fewer than eight conversations started, any conversation ended with `error:*`, or any conversation made no request. An `error:*` in one conversation (for example a protocol error from invalid tool-call JSON or an empty command) is recorded as the exception class only and the run **continues** with the next conversation, ending INCOMPLETE. Growth is not assessed (`not_assessed_run_incomplete`) and no growth reason is reported when the run is incomplete, so a setup or provider abort is never presented as a growth failure; safety reasons (G1, G2) still apply. Incomplete data are reported but not interpreted; one resubmission is allowed for a setup failure (hash/commit mismatch, VRAM-guard stop, server not ready, `n_ctx` mismatch) with unchanged analysis.
- **G4 (growth; evaluated only for a complete run).** A "terminal-turn delta" is the increase in preflight prompt tokens from a request whose reply was a valid terminal call to the next request. INVALID if either condition has fewer than **8** such deltas (the four-terminal instruction gives up to 4 per conversation, so up to 16 per condition), or if the median long delta exceeds the median short delta by less than 400 tokens. Rationale: the long observation is <= 3,600 characters at roughly 2.5 characters per token (about 1.3k to 1.5k tokens) against a short one of about 90 characters (about 25 to 40 tokens); 400 tokens is roughly a third of the expected difference, leaving margin for the shared assistant-message component, and is fixed a priori and **not** to be revisited after seeing data.

Stop rules during the run: per conversation, the 12-request ceiling and the context guard. The run **hard-aborts** only on a VRAM-monitor/guard failure or other `SafeDiagnosticError`, or on a new step-log-like file. A single conversation's `error:*` (class recorded) does not abort the run. No retries, resampling or setting changes after outcomes are seen, other than the single G3 resubmission. Wall limit 1 hour; expected well under 20 minutes.

## 7. Analysis plan

After the gate: print the per-conversation ordered tables (categories, finish reasons, token counts, recovery events) and per-conversation counts for H1 to H3, then H5. Report counts with denominators and per conversation (for example "k of n first requests", "conversations with at least one no-tool reply: j of 8"). Requests are clustered within 8 conversations (4 pairs), so a pooled request-level binomial bound would be misleading and none is computed. No p-values, intervals or effect sizes, and no pooling with v1.

## 8. Honest limits

- **Conversation length is still behaviour-dependent.** The instruction asks for exactly four terminal calls then a submission, but the model may submit early, loop, or emit no-tool replies. Growth over turns exists only if it keeps calling `terminal`. If fewer than 8 terminal-turn deltas per condition result, G4 marks a complete run INVALID rather than let a thin contrast pass. The changed instruction also makes a "do what you are told" test of the model, not only of the interface.
- **Growth here is observation size per turn**, not a model of realistic code or test output. The synthetic text (counter-derived records) is unlike real terminal output; tokenisation and model response to it are untested.
- **Identical first request does not guarantee identical trajectories** later (different observations, serving nondeterminism); pairing controls the first request only.
- **Reasoning-token counts may be unavailable.** If the server omits `completion_tokens_details`, only character counts exist and H2 readings (i) to (iii) are weaker. `finish_reason` availability depends on the server; absent values are recorded as `unavailable`.
- **Gate proxies are not proofs.** G1 relies on a Popen wrapper (it does not see in-process `os.system`-style calls), a module-name heuristic, and file checks; hard-coded "no executor" flags from v1 were replaced by these measured proxies, but they remain proxies, with code review as the backstop. The module heuristic could in principle flag a benign lazy import and produce a false INVALID; that is accepted as the conservative error.
- **Small n, one model, one seed root, one GPU, 32,768 window, 1 slot.** No generalisation to other windows, caps, samplers, the real Harbor control channel, container isolation, the verifier, or S0's 60-step behaviour. The 12-request ceiling truncates the target: "no submit by ceiling" is not "never submits".
- **v1 and v2 differ in window, ceiling, README and observations**, so v2 cannot be used to say whether the 35% no-tool rate in v1 was an artifact of the 8,192 window; it only characterises v2's stimulus.
- **Testing.** The gate, order recording, guard arithmetic and aggregate-only machinery are covered by offline unit tests with a stub client (`tests/test_s0_history_check_v2.py`); no live server, GPU or Slurm path has been exercised, and the sbatch has had only a shell syntax check.

**Outcomes (descriptive, n = 8 conversations, 43 requests).**
- Every conversation made exactly four `terminal` calls and then called `submit` (8/8), i.e. the v2 instruction was followed in all conversations. Instruction-following is therefore part of what was measured.
- No schema-invalid JSON in 43 requests (32 `valid_schema_A`, 8 `valid_schema_B`, 3 `no_tool_call`).
- All 3 `no_tool_call` responses occurred at request 5, immediately after the fourth `terminal` call and before `submit`. In each, `finish_reason` was `stop` with 11-12 completion tokens (a short plain-text reply instead of the `submit` tool call). All 3 were `recovered`: the next request was a valid `submit`. Short condition: 2 of 4 conversations; long: 1 of 4. With n = 4 per arm this does not support any claim about history length.
- Reasoning-token counts were `unavailable` in every request (the server returned none), as anticipated in Sec. 8.

**Reading, with limits.** The pattern is consistent with the model sometimes ending its turn in prose at the moment it considers the task finished, rather than invoking the `submit` tool, and with the agent's single nudge recovering it. This is a hypothesis from 3 events in one run, not an established cause. It is consistent with v1's 35% no-tool rate, but v1 did not record request order, v1's instruction and README differ, and v1 used an 8,192 window, so v1 and v2 are not comparable (Sec. 8) and the v1 rate is not explained by this run. The 3 events could also reflect sampling variation.

**Unexplained observation to check.** In the three conversations with a `no_tool_call`, the prompt-token count of the following (`submit`) request is lower than that of the `no_tool_call` request (e.g. 1,176 to 913; 6,294 to 6,066). Code check (`environments/harbor_agent.py`, lines ~299-304): after a reply without a tool call the agent appends the assistant message and then a user message, "Protocol error: return a terminal or submit tool call.", so the message list grows. The recovery is therefore a response to that fixed nudge, not spontaneous. The shorter token count must come from how the server renders or counts the prompt (a chat-template effect on earlier assistant turns is one candidate); this was not verified.

**Not shown.** Behaviour on real task text, real tool output, long histories near the window, or any benchmark; throughput; reproducibility across seeds or model builds. Nothing here authorizes a task pilot.
