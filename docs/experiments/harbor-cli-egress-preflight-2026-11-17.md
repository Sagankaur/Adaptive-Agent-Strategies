## Rerun history and correction

The first complete CLI run, job **4801507**, passed its original checks, but an independent review found that the provider ignored `read_only: true` in Harbor bind configuration. Its captured argv lacked `:ro` on `/wheels` and `/runtime-deps`, so those mounts were writable by default. The task did not attempt to modify them, but that run did not establish safe dependency mounts. The original partial result is preserved in [result.json](artifacts/harbor_cli_4801507/result.json).

The provider patch now translates `read_only: true` into Apptainer's `:ro` bind suffix, and the fixture verifies the effective mount flags from `/proc/self/mountinfo`. Two intermediate reruns failed before a task started: **4801510** had a malformed duplicate patch section, and **4801511** lacked the provider's `disable_internet` capability declaration. Neither ran a task. Job **4801512** is the corrected successful run and its result is recorded in [result.json](artifacts/harbor_cli_4801512/result.json).

The corrected run also logged `su: Authentication failure` during Harbor's best-effort main-service artifact collection. The pinned Harbor artifact handler asks whether artifact paths are directories using `user="root"`; the unprivileged provider translates that request to `su root`, which cannot elevate in this container. Harbor catches that check failure and falls back to inferring file versus directory from the path suffix, so the synthetic verifier still returned reward `1.0`. This confirms that explicit root operations are unsupported; it does not establish complete artifact collection or compatibility with tasks whose setup or tests require root. No password was entered.

## Scope and next gate

The corrected run establishes that a synthetic trial can use Harbor's normal CLI lifecycle while the tested Apptainer network namespace blocks the recorded external, DNS, IPv6, and metadata probes, Harbor control continues over a private Unix socket, and the two staged dependency mounts are read-only. It also exposes that explicit `user="root"` operations fail under this unprivileged setup. It does **not** establish Aider task-image fidelity, arbitrary task compatibility, complete artifact collection, complete credential absence, hard per-task resource enforcement, agent/model behavior, or benchmark performance.

Next, reproduce the exact pinned Aider runtime in an Apptainer-compatible task image, verify whether its commands and artifact collection require root, and resolve the resource-limit question. Keep model-driven episodes paused until these checks are complete. The six-task Aider pilot must then use frozen task IDs and its official verifier; it remains exploratory feasibility evidence. This does not change the primary proposal or any existing benchmark gate.

## Source for the artifact-collection behavior

The pinned Harbor v0.23.0 [`ArtifactHandler`](https://github.com/harbor-framework/harbor/blob/1e5c5c6db929a10a140d05e606882c671ae20729/src/harbor/trial/artifact_handler.py) checks artifact paths with `user="root"` and falls back to inferring the path type if that check raises. The pinned [Apptainer provider](https://github.com/harbor-framework/harbor/blob/1e5c5c6db929a10a140d05e606882c671ae20729/src/harbor/environments/singularity/singularity.py) wraps explicit user requests with `su`; without fakeroot, root elevation fails as observed.
