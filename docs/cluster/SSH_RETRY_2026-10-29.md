## Rohan CPU Harbor smoke attempts — 2026-10-30

- Job `4385208` failed during Harbor environment validation. The task requested `allow_internet = false`, which Harbor translates to `network_mode='no-network'`; Harbor v0.23.0's Singularity provider does not advertise support for enforcing that policy.
- Job `4385234` passed task validation and pulled `python:3.12-slim`, but Harbor's container bootstrap failed before the agent ran. The site Singularity runtime reported that `--writable-tmpfs` was disabled because the container was using underlay. The image was read-only, so Harbor could not create `/app`; the image also lacked `/usr/bin/python3`, and bootstrap could not install it. Harbor recorded one errored trial and zero completed trials.
- Both jobs are finished. No task command ran, the verifier did not run, and there is no reward or episode telemetry to report. The second job's image cache was under node-local `/tmp`, not the persistent scratch cache.

The system Singularity 3.7.1 runtime failed Harbor bootstrap because it could not provide the writable task filesystem Harbor expects. Continue only after a cluster runtime with Harbor-compatible writable container support is available, or after a separately reviewed adapter/runtime change. Do not use this failed smoke as evidence that the adapter ran successfully.

## Apptainer capability probe - 2026-10-30

The Rohan CPU Slurm node exposes Apptainer 1.3.3 through the `apptainer` module. The login node's ordinary `singularity` command remains Singularity 3.7.1; loading the module in a login-shell Slurm job does not put an Apptainer-compatible `singularity` command ahead of that executable.

A five-minute CPU Slurm capability probe on `cpu-f-01` confirmed:

- `apptainer exec docker://alpine:3.20 ...` pulled and ran the image.
- `apptainer exec --containall --writable-tmpfs --fakeroot ...` created a file in the writable temporary filesystem.
- `apptainer exec --containall --fakeroot --net --network none ...` succeeded with network namespace isolation enabled.
- A probe using `--pwd /app` failed because `/app` did not exist in the Alpine image; Apptainer changes directory before executing the command. This does not test writable tmpfs, which passed independently.

These results establish that the compute-node Apptainer module supports the required primitives in this CPU test. They do not establish that Harbor works with this module. Harbor v0.23.0 invokes `singularity exec`, passes `--pwd /app` and `--writable-tmpfs`, and its provider rejects tasks requesting no internet. A Harbor job would need a job-local `singularity` wrapper pointing to the module's Apptainer binary, plus an image with `/app` and the needed Python/server dependencies already present. Network isolation remains unresolved: the Harbor provider does not pass Apptainer's `--net --network none`, and using that option may break Harbor's localhost command-server connection. Do not treat the capability probe as a Harbor trial or benchmark result.

The integration smoke below confirms Harbor can run a scripted CPU task through the Slurm Apptainer module. Before benchmark or provider-backed runs, ask A2I2 support whether Apptainer 1.3.3 is approved and what policy can block task egress while preserving Harbor's loopback control connection. The successful smoke does not close the network-isolation gate.

### Harbor Apptainer integration attempt - 2026-10-30

Build and a `--pwd /app --writable-tmpfs --fakeroot --containall` execution check completed successfully. A job-local `singularity` wrapper then routed Harbor v0.23.0 to the module binary.

The subsequent one-trial synthetic Harbor job (`4388608`) started Harbor's FastAPI command server inside the SIF and performed the fixed terminal and submit steps, but it did not produce a valid trial result. The scripted model stub failed with `EADDRINUSE` on fixed port 8765. The agent log nevertheless contains the two scripted responses, so the source of those responses is unresolved; do not use this run as evidence of a successful stub-backed trial. Harbor then failed grading with `RewardFileNotFoundError`, and recorded zero completed trials. No benchmark task or provider credentials were used.

The failed attempt exposed two issues. A retry must avoid fixed port 8765 and confirm its own stub is listening before Harbor starts. The task verifier also contained mixed line endings, which made the final `fi` invalid to `/bin/sh`.

## Non-container alternatives checked - 2026-10-30

Harbor 0.23.0 was inspected in the Rohan virtual environment. Its built-in environment registry has no host-process or local-shell environment type, so changing `environment.type` to a direct-host option is not supported. The available built-in alternatives are remote/container services such as Daytona, E2B, Modal, Runloop, and OpenSandbox; using those would require an approved external service, credentials, and network access, and would move execution off the university cluster.

On the Rohan login node, `docker`, `singularity`, and `runc` are present; `podman`, `apptainer`, and `crun` are not on the login-node PATH. Docker was already checked and the account cannot access its daemon socket. Apptainer is available as a compute-node module under Slurm, as described above. The presence of `runc` alone does not provide a configured runtime or Harbor integration.

A task could be run by manually invoking project code in a user virtual environment, but that would bypass Harbor's task lifecycle and provide no task filesystem or network isolation. No direct-host Harbor trial was launched: with the current cluster configuration, there is no supported host execution backend to test, and running task code directly on a shared node would not be an acceptable substitute for an isolated smoke.
